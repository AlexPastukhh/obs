## S-001

**Concept: what compression means in HTTP.** The sender encodes body bytes with an algorithm such as gzip, deflate, or Brotli to make the body smaller; the receiver decodes it. Benefits: smaller payload, less bandwidth, often faster overall on slower links. Trade-off: CPU is spent compressing and decompressing.

---

## S-042

**`leaveOpen: true`.** Disposing `gzip` must not close the underlying memory stream because the code still needs `ms` for `StreamContent` after gzip finalization.

---

## S-031

**Sending data compressed.** This is request compression: compress the JSON payload with `GZipStream`, then set `Content-Encoding`.

---

## S-002

**Two directions — response compression.** Typical flow: client sends `Accept-Encoding: gzip, br, deflate`; server selects a supported algorithm, returns `Content-Encoding`, and sends compressed body bytes; client decompresses automatically when configured or manually otherwise.

---

## S-026

**HttpClient automatic response decompression.** Configure the primary `SocketsHttpHandler.AutomaticDecompression`. The handler can advertise acceptable encodings and transparently decompress the response body before application code reads it.

---

## S-036

**What the client code does.** Create `MemoryStream`; wrap it in `GZipStream`; serialize JSON into gzip; dispose gzip to finalize it; rewind the memory stream; send it through `StreamContent`; set `Content-Type: application/json` and `Content-Encoding: gzip`.

---

## S-035

**Client method that posts gzipped JSON.**

```csharp
public static async Task<HttpResponseMessage> PostGzippedJsonAsync<T>(
    HttpClient client,
    string url,
    T payload,
    JsonSerializerOptions options,
    CancellationToken ct)
{
    await using var ms = new MemoryStream();

    await using (var gzip = new GZipStream(
        ms,
        CompressionLevel.Fastest,
        leaveOpen: true))
    {
        await JsonSerializer.SerializeAsync(
            gzip, payload, options, ct);
    }

    ms.Position = 0;

    using var request = new HttpRequestMessage(HttpMethod.Post, url);
    request.Content = new StreamContent(ms);
    request.Content.Headers.ContentType =
        new MediaTypeHeaderValue("application/json");
    request.Content.Headers.ContentEncoding.Add("gzip");

    return await client.SendAsync(request, ct);
}
```

---

## S-043

**What would happen with `leaveOpen: false`.** Disposing the gzip wrapper would also close `ms`, and later `StreamContent(ms)` would fail.

---

## S-044

**Why nested `await using` braces matter.** The inner block ensures gzip is disposed before `ms` is rewound and sent. Disposal flushes/finalizes the gzip trailer and remaining compressed bytes; sending before disposal can produce incomplete/corrupt data.

---

## S-003

**Request compression.** Useful for large JSON or file uploads. Client compresses the request body, sends `Content-Encoding: gzip`, and the server decompresses according to that header. Response compression is commonly enabled; request decompression is not automatically enabled in every setup.

---

## S-027

**Named HttpClient configuration.**

```csharp
builder.Services.AddHttpClient("Api", client =>
{
    client.BaseAddress = new Uri("https://api.example.com/");
})
.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
{
    AutomaticDecompression =
        DecompressionMethods.GZip |
        DecompressionMethods.Deflate |
        DecompressionMethods.Brotli
});
```

## S-037

**Is `MemoryStream` required?** No. Some stream is needed to hold or send the compressed bytes. `MemoryStream` is convenient because the code can compress, rewind, and send.

## S-032

**Headers.** Request: `Content-Type: application/json` and `Content-Encoding: gzip`. A compressed response may independently contain `Content-Encoding: gzip`.

## S-028

**Reading an automatically decompressed response.**

```csharp
var client = httpClientFactory.CreateClient("Api");

using var response = await client.GetAsync(
    "movies/123/posters/456",
    HttpCompletionOption.ResponseHeadersRead,
    ct);

response.EnsureSuccessStatusCode();

// Content is already decompressed if the server sent gzip/br.
await using var stream =
    await response.Content.ReadAsStreamAsync(ct);

var poster = await JsonSerializer.DeserializeAsync<PosterDto>(
    stream,
    cancellationToken: ct);
```

## S-040

**`CompressionLevel.Fastest`.** It emphasizes speed over maximum compression ratio, generally producing a slightly larger payload. Good when CPU and latency matter and payloads are moderate.

---

## S-033

**Server-side response compression.** ASP.NET Core supports server-to-client response compression through response-compression middleware.

---

## S-038

**Buffering trade-off.** `StreamContent(ms)` is simple and good for small/medium payloads, but the entire compressed request body is buffered in memory and is not ideal for very large payloads.

---

## S-067

**Compression decision factors.** Compression is useful, not “always on.” Consider payload size, content type, CPU budget, network speed/latency, and client/server support.

## S-034

**ASP.NET Core response-compression registration.**

```csharp
builder.Services.AddResponseCompression(options =>
{
    options.EnableForHttps = true;
    options.Providers.Add<GzipCompressionProvider>();
    options.Providers.Add<BrotliCompressionProvider>();
});

builder.Services.Configure<GzipCompressionProviderOptions>(o =>
{
    o.Level = CompressionLevel.Fastest;
});

builder.Services.Configure<BrotliCompressionProviderOptions>(o =>
{
    o.Level = CompressionLevel.Fastest;
});

var app = builder.Build();
app.UseResponseCompression();
```

## S-029

**Key point.** Application code still “reads a stream,” but automatic decompression makes that stream contain decompressed bytes.

---

## S-039

**Avoiding `MemoryStream`.** More advanced choices include a custom `HttpContent` that compresses while writing to the network, or pipe/producer-consumer streaming patterns. For most moderate payloads, `MemoryStream` is practical.

---

## S-041

**Other compression levels.** `Optimal` gives better compression but is slower; `NoCompression` is effectively no compression; `SmallestSize` targets the best size and may be slower when available.

---

## S-068

**Good candidates.** Text-based non-tiny payloads such as JSON, XML, HTML, CSS, JavaScript, CSV, and plain text usually compress well.

---

## S-069

**Size/network rules of thumb.** Under roughly 1 KB is usually not worth it; 1–10 KB depends; over 10 KB often helps; very large text usually benefits. Compression helps more on mobile/slow/high-latency links and repeated JSON structures.

---

## S-070

**Do not recompress already compressed payloads.** JPEG/PNG/WebP/GIF, MP4/MP3/AAC, ZIP/RAR/7z/gzip, and many PDFs gain little, waste CPU, and can become larger.

---

## S-074

**Do provider options always need configuration?** No. Configure them only when response compression is enabled and non-default behavior is needed. Registering providers and using middleware can be enough. Manual stream compression is configured where the stream is created, not through response-compression provider options.

---

## S-004

**ASP.NET Core request decompression.** When supported, register request-decompression services and middleware. Otherwise inspect `Content-Encoding` and wrap `Request.Body` in a decompression stream manually.

```csharp
builder.Services.AddRequestDecompression();

var app = builder.Build();
app.UseRequestDecompression();
```

---

## S-073

**Common header example.**

```http
Vary: Accept-Encoding
```

If one client accepts gzip and another does not, cache entries must be kept separate because response bytes differ.

---

## S-071

**Tiny payload or CPU bottleneck.** Header and CPU overhead can outweigh savings for small bodies. When CPU is hot, compress less aggressively, compress only larger responses, or use `Fastest` instead of `Optimal`.

---

## S-007

**What built-in request decompression does internally.** Middleware reads `Content-Encoding`, wraps `Request.Body` with the correct decompression stream, then MVC model binding reads decompressed JSON and `[FromBody]` works normally.

---

## S-072

**`Vary: Accept-Encoding`.** ASP.NET Core response-compression middleware normally sets the needed headers when it compresses. Add `Vary` manually only when custom code produces different bytes by `Accept-Encoding` and it is not already set. This prevents cache poisoning/mixing compressed and identity variants.

---

## S-018

**Built-in middleware and multiple encodings.** The source states that the built-in ASP.NET Core request-decompression middleware does not handle multiple `Content-Encoding` values on one request; when it cannot decompress, the request may pass through. Multi-encoding support therefore needs a custom chain/registry implementation.

---

## S-008

**Manual request decompression.** Check `Content-Encoding` and replace `Request.Body`. Useful for older setups, custom behavior, or only selected endpoints supporting gzip.
