## Screenshot-backed transcript

This region distinguishes the two directions of HTTP content coding.

- **Response compression:** the client advertises acceptable algorithms with `Accept-Encoding`; the server chooses an encoding and returns `Content-Encoding`. ASP.NET Core response-compression middleware should vary cacheable responses by `Accept-Encoding`.
- **Request compression:** the client compresses the request body and sends `Content-Encoding`; the server must explicitly support request decompression. Response decompression support does not imply request decompression support.
- `SocketsHttpHandler.AutomaticDecompression` transparently unwraps compressed response bodies, so callers still consume the result as a stream of decoded bytes.
- The client example compresses JSON into a stream, disposes the compression wrapper so its footer/final bytes are written, rewinds the underlying stream and sends it with `StreamContent`.
- `leaveOpen: true` preserves the underlying stream after disposing `GZipStream`; without it the stream needed by `StreamContent` would also be closed.
- `CompressionLevel.Fastest` trades compression ratio for lower CPU cost. Compression should be selective: useful for medium/large text payloads and slow links, usually wasteful for tiny bodies or formats already compressed such as JPEG, PNG, MP4, ZIP and many PDFs.
- Provider options only need explicit configuration when defaults or enabled algorithms must change.
