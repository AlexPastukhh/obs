## 0.1 Area overview / key ideas / reading quality

What this area is about:
- SaveChanges lifecycle versus command execution.
- Values generated by database/provider and when EF receives them.
- Why intermediate SaveChanges may be needed for generated IDs or phase flushes.
- Large import batching, memory, change tracking, and failure recovery.
- ChangeTracker.Clear and short-lived DbContext safety rules.
- Manual savepoints when business rollback boundaries differ from every SaveChanges call.

Key ideas:
- SaveChanges interceptors are tied to the SaveChanges lifecycle, while command interceptors are tied to actual database command execution.
- A later transaction rollback does not undo the fact that SaveChanges/command interceptors already ran.
- Generated values can be database-generated during INSERT/UPDATE or provider/client-generated before INSERT.
- EF can populate generated values back into tracked entities after SaveChanges.
- You may need an intermediate SaveChanges when a later step needs a generated ID outside EF relationship fix-up.
- For parent/child graph inserts, EF can often insert everything in one SaveChanges and fix up generated keys.
- One giant SaveChanges for huge imports creates memory/change-tracker/batch/error-recovery problems.
- SaveChanges per row is usually worst; chunked SaveChanges is the practical compromise.
- SaveChanges alone does not reduce memory; ChangeTracker.Clear or disposing a short-lived DbContext does.
- ChangeTracker.Clear is a big hammer: it clears everything tracked by that context.
- Fresh DbContext per chunk or separate contexts for separate phases avoid accidental detach bugs.
- Manual savepoints are useful when rollback boundaries are business phases, not every SaveChanges call.

SaveChanges interceptors

A SaveChangesInterceptor can run around the high-level SaveChanges() call. EF Core docs describe interceptors as allowing interception of both low-level database operations such as commands and higher-level operations such as calls to SaveChanges.

SavingChanges     before EF saves

## 3. Cleaned source notes

- SaveChanges interceptors can observe a successful SaveChanges even if an outer transaction rolls back later.
- Command interceptors observe actual database commands, so if no command is sent, command interceptors may not run.
- Generated values may be returned by the database after INSERT/UPDATE, or generated by EF/provider before SQL is sent.
- Calling SaveChanges just to get a parent ID is unnecessary for normal parent/child graphs; EF can often order commands and fix up generated keys.
- Intermediate SaveChanges is useful when the generated ID or previous database write must be consumed outside EF relationship fix-up.
- For huge imports, one giant SaveChanges creates change tracker and failure recovery problems; SaveChanges per row creates too many flushes/round trips.
- Chunked SaveChanges is the usual EF compromise for large imports, but real bulk APIs may be better for very large loads.
- Memory reduction comes from ChangeTracker.Clear or disposing the DbContext, not from SaveChanges alone.
- Use Clear only when the context is dedicated to temporary batch tracking, because it detaches everything.
- Fresh DbContext per chunk or separate contexts for separate phases reduces accidental detach risk.
- Manual savepoints are valuable when rollback should happen at a business phase boundary.
