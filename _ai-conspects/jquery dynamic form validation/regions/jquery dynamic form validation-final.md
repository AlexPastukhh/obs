# jQuery dynamic form validation — final source-preserving transcript

## 0.1 Area understanding / reading quality

This conspect explains how ASP.NET Core data annotations become HTML `data-val-*` attributes, how jQuery Validate and jQuery Validate Unobtrusive consume them, and what must be done when a form is injected dynamically.

Reading quality is high. The generated HTML and Razor snippets are preserved as source images.

## 1. Required scripts

The usual client stack is:

- jQuery;
- `jquery.validate`;
- `jquery.validate.unobtrusive`.

ASP.NET Core's unobtrusive package reads validation metadata generated into HTML and configures the underlying jQuery Validate engine.

The server still remains authoritative. Client validation improves UX but does not replace model binding, data annotations, `ModelState`, or server-side business validation.

## 2. How ASP.NET Core generates rules

A view model with attributes such as `[Required]`, `[EmailAddress]`, `[StringLength]`, `[Range]`, and related validators is rendered by Razor tag helpers into inputs containing attributes such as:

```html
data-val="true"
data-val-required="..."
data-val-email="..."
data-val-length="..."
data-val-range="..."
```

`asp-for`, `asp-validation-for`, and `asp-validation-summary` generate the field names, inputs and validation placeholders. The unobtrusive adapter maps `data-val-*` attributes into jQuery Validate rules and messages.

Client-side validation covers rules expressible in these attributes. Some rules remain server-only, such as checking whether an email already exists, whether a value is unique, or whether a user may edit a record.

## 3. Partial views

A form can live in a partial view. Script references should not be duplicated in every partial; normally the page or layout loads jQuery once, while the validation script partial is included at an appropriate page level.

A partial that contains only markup is safe to inject dynamically. It still carries its `data-val-*` metadata because those attributes were produced on the server.

## 4. Dynamic form injection

When HTML is inserted after initial page load—for example through `fetch`, AJAX or a modal—the browser receives valid markup, but the unobtrusive library may not automatically scan the new form.

After insertion, explicitly parse the new form or container:

```javascript
$.validator.unobtrusive.parse(formOrContainer);
```

This makes jQuery Validate discover the newly added `data-val-*` attributes, attach handlers, block invalid submission and show messages.

Without the parse step, the server-side rules are still enforced after submission, but the dynamically inserted form may show no client-side validation.

## 5. jQuery Validate and custom rules

jQuery Validate performs the actual browser-side checks. It runs configured rules, displays messages, adds/removes CSS classes and controls whether submission is allowed.

The unobtrusive package is mainly an adapter from ASP.NET Core's generated attributes to jQuery Validate.

Manual JavaScript rules can be defined directly with `.validate({...})`, but forms generated by Razor tag helpers generally should reuse the unobtrusive metadata rather than duplicate validation definitions.

## 6. Server errors and ModelState

When server validation fails, controllers add errors to `ModelState` and return the view/partial again. Razor validation helpers render those messages into the returned HTML.

Business or authorization errors can be added manually with `ModelState.AddModelError(...)`. After replacing the form markup with the returned partial, parse the new markup again when client-side behavior must continue.

The complete flow is therefore:

```text
server generates rules -> Razor renders data-val attributes
browser inserts form -> unobtrusive.parse scans it
jQuery Validate handles immediate UX
server model binding and ModelState enforce correctness
returned partial renders server errors consistently
```
