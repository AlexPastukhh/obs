Yes.

## 1) Is there overhead when savepoints are created in a large batch?

Yes, usually **some overhead**.

A savepoint is a real transaction checkpoint. EF exposes `CreateSavepoint`, `RollbackToSavepoint`, and `ReleaseSavepoint`, and the docs for `ReleaseSavepoint` explicitly say releasing it allows the system to reclaim some resources before the transaction ends. That implies savepoints are not free objects; they consume transaction-related resources until released or until the transaction ends. ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/microsoft.entityframeworkcore.storage.idbcontexttransaction.releasesavepointasync?view=efcore-9.0&utm_source=chatgpt.com "IDbContextTransaction.ReleaseSavepointAsync(String ..."))

So in a large batch like this:

```csharp
await using var tx = await db.Database.BeginTransactionAsync();

foreach (var chunk in chunks)
{
    db.Items.AddRange(chunk);
    await db.SaveChangesAsync(); // auto-savepoint before each SaveChanges if enabled
}

await tx.CommitAsync();
```

with `AutoSavepointsEnabled = true`, EF will create a savepoint before each `SaveChanges()` inside that manual transaction. More `SaveChanges()` calls means more savepoint work. EF documents that automatic savepoints are created for `SaveChanges` inside an existing transaction when supported, and manual savepoint APIs exist because they are distinct transaction operations. ([Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/saving/transactions?utm_source=chatgpt.com "Transactions - EF Core"))

So the practical answer is:

- one big transaction + many `SaveChanges()` calls + auto savepoints = **extra savepoint operations**
    
- that means **some additional cost** in transaction bookkeeping/resources
    
- whether it matters depends on how many chunks you have and how sensitive that path is
    

That is why your earlier intuition was basically right: in a large batch, you may prefer either:

- keep auto savepoints on because mid-batch recovery matters, or
    
- turn them off and treat any failure as “rollback whole transaction”, or
    
- turn them off and place **one or two manual savepoints** at meaningful business boundaries instead of before every `SaveChanges()` call. ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/microsoft.entityframeworkcore.storage.idbcontexttransaction?view=efcore-10.0&utm_source=chatgpt.com "IDbContextTransaction Interface"))
    

The safest summary is: **yes, there is overhead, but it is usually transaction/safety overhead, not something you optimize away unless you have a real batching reason**. The docs do not give a numeric cost, so that part is an engineering inference from the fact that savepoints are real transaction operations with reclaimable resources. ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/microsoft.entityframeworkcore.storage.idbcontexttransaction.releasesavepointasync?view=efcore-9.0&utm_source=chatgpt.com "IDbContextTransaction.ReleaseSavepointAsync(String ..."))

## 2) Isolation levels in the context of retries, especially retrying in the same transaction

The key idea is this:

**Whether retrying in the same transaction makes sense depends on what view of data that transaction can see after the retry.**

If the transaction can see a **fresher committed state** on retry, same-transaction retry may make sense.  
If the transaction is stuck with the **same old snapshot/locks** until commit or rollback, retrying in the same transaction is usually pointless. ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql?view=sql-server-ver17&utm_source=chatgpt.com "SET TRANSACTION ISOLATION LEVEL (Transact-SQL)"))

I’ll focus on the SQL Server-relevant levels you’re most likely to use from EF.

### `ReadCommitted`

This is SQL Server’s default isolation level. SQL Server says it prevents dirty reads, but data can be changed by other transactions **between individual statements** in the current transaction, so nonrepeatable reads and phantoms can occur. That means a later statement in the same transaction may see newer committed data than an earlier statement. ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql?view=sql-server-ver17&utm_source=chatgpt.com "SET TRANSACTION ISOLATION LEVEL (Transact-SQL)"))

That makes `ReadCommitted` the **most natural level for same-transaction retry** after rollback to a savepoint.

Practical pattern:

```csharp
await using var tx =
    await db.Database.BeginTransactionAsync(System.Data.IsolationLevel.ReadCommitted);

var saved = false;

while (!saved)
{
    try
    {
        var person = await db.People.SingleAsync(x => x.Id == id);
        person.Name = newName;

        await db.SaveChangesAsync();
        saved = true;
    }
    catch (DbUpdateConcurrencyException ex)
    {
        foreach (var entry in ex.Entries)
        {
            var dbValues = await entry.GetDatabaseValuesAsync();
            if (dbValues is null) throw; // deleted

            entry.OriginalValues.SetValues(dbValues);
        }
    }
}

await tx.CommitAsync();
```

Why this can work in the **same transaction**:

1. manual transaction starts
    
2. EF creates a savepoint before `SaveChanges()` if enabled/supported
    
3. save fails with concurrency conflict
    
4. EF rolls back to the savepoint
    
5. your next query can see the latest committed state for that new statement under `ReadCommitted`
    
6. you retry and may succeed without starting a brand-new transaction ([Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/saving/transactions?utm_source=chatgpt.com "Transactions - EF Core"))
    

### `ReadCommitted` with `READ_COMMITTED_SNAPSHOT` enabled

This is still `ReadCommitted`, but SQL Server uses **row versioning** instead of shared locks for reads. SQL Server says each statement sees the committed version as of the **start of that statement** when `READ_COMMITTED_SNAPSHOT` is on. ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql?view=sql-server-ver17&utm_source=chatgpt.com "SET TRANSACTION ISOLATION LEVEL (Transact-SQL)"))

That is also good for same-transaction retry, often even better from a concurrency standpoint, because your retry query can see a fresh committed version for the new statement without relying on long read locks. SQL Server’s deadlock guidance even recommends row-versioning-based `READ COMMITTED` for many applications. ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-deadlocks-guide?view=sql-server-ver17&utm_source=chatgpt.com "Deadlocks Guide - SQL Server"))

So for “retry in the same transaction after savepoint rollback”, the best practical bucket is:

- `ReadCommitted`
    
- `ReadCommitted` + RCSI (`READ_COMMITTED_SNAPSHOT ON`) ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql?view=sql-server-ver17&utm_source=chatgpt.com "SET TRANSACTION ISOLATION LEVEL (Transact-SQL)"))
    

### `RepeatableRead`

EF’s concurrency docs say that under SQL Server’s repeatable read, when you query a row your transaction takes a shared lock on it, and a concurrent updater is blocked until your transaction completes. SQL Server’s locking guide also says stricter levels like `REPEATABLE READ` hold row/page locks until the end of the transaction. ([Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/saving/concurrency?utm_source=chatgpt.com "Handling Concurrency Conflicts - EF Core"))

That means same-transaction retry is usually **not the interesting pattern** here.

Why:

- if you already read the row, your transaction may be holding locks
    
- other writers are blocked rather than “winning and giving you newer data”
    
- retrying inside the same transaction usually does not give you a meaningfully fresher view
    
- keeping the same transaction alive just prolongs blocking and deadlock risk ([Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/saving/concurrency?utm_source=chatgpt.com "Handling Concurrency Conflicts - EF Core"))
    

So with `RepeatableRead`, the better guidance is usually:

- keep the transaction very short, or
    
- roll back and start a new transaction instead of retrying inside the same one ([Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/saving/concurrency?utm_source=chatgpt.com "Handling Concurrency Conflicts - EF Core"))
    

### `Serializable`

This is even stricter. SQL Server says it holds read and write locks until the end of the transaction and also uses range locks to prevent phantom reads. It provides the strongest isolation, but at a high concurrency cost. SQL Server’s deadlock guidance explicitly says to avoid higher isolation levels like `REPEATABLE READ` and `SERIALIZABLE` when not required. ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide?view=sql-server-ver17&utm_source=chatgpt.com "Transaction locking and row versioning guide - SQL Server"))

So same-transaction retry under `Serializable` is usually a poor fit:

- you are deliberately holding the strongest locks
    
- retrying in the same transaction tends to preserve the same lock footprint
    
- you often do not get the “fresh re-read and try again” benefit you want
    
- rolling back and starting over is usually cleaner if a retry is needed ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide?view=sql-server-ver17&utm_source=chatgpt.com "Transaction locking and row versioning guide - SQL Server"))
    

### `Snapshot`

This is the big one.

EF’s concurrency docs say snapshot isolation is an optimistic approach where another transaction may update the row, but when your transaction later tries to update, a serialization/concurrency error is raised. SQL Server says under snapshot isolation, data read by any statement in the transaction is the committed version that existed at the **start of the transaction**. ([Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/saving/concurrency?utm_source=chatgpt.com "Handling Concurrency Conflicts - EF Core"))

That means:

**retrying in the same transaction is usually not useful under `Snapshot`.**

Why:

1. transaction starts
    
2. it gets a snapshot of data as of transaction start
    
3. another transaction commits a conflicting change
    
4. your update fails with a serialization/update conflict
    
5. if you retry in the same transaction, you still have the same transaction-start snapshot
    
6. so you usually do **not** get a fresher view by retrying there
    

In practice, under `Snapshot`, the right retry unit is usually:

- rollback the whole transaction
    
- start a **new transaction**
    
- re-read under the new snapshot
    
- try again ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql?view=sql-server-ver17&utm_source=chatgpt.com "SET TRANSACTION ISOLATION LEVEL (Transact-SQL)"))
    

That is the cleanest “same transaction vs new transaction” dividing line.

### `ReadUncommitted`

This allows dirty reads and is the least restrictive isolation level. It is generally not what you want for update/retry correctness logic. SQL Server says this level allows reading uncommitted modifications. ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql?view=sql-server-ver17&utm_source=chatgpt.com "SET TRANSACTION ISOLATION LEVEL (Transact-SQL)"))

So in the context of “retrying safely after conflict”, `ReadUncommitted` is basically: **do not build correctness-sensitive retry logic around this**. ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql?view=sql-server-ver17&utm_source=chatgpt.com "SET TRANSACTION ISOLATION LEVEL (Transact-SQL)"))

## The short practical rule

If your question is specifically: **“When can I retry after rollback to savepoint in the same transaction?”**

Best fit:

- `ReadCommitted`
    
- `ReadCommitted` with `READ_COMMITTED_SNAPSHOT ON` ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql?view=sql-server-ver17&utm_source=chatgpt.com "SET TRANSACTION ISOLATION LEVEL (Transact-SQL)"))
    

Usually not a good fit:

- `RepeatableRead`
    
- `Serializable` ([Microsoft Learn](https://learn.microsoft.com/en-us/ef/core/saving/concurrency?utm_source=chatgpt.com "Handling Concurrency Conflicts - EF Core"))
    

Usually the wrong fit for same-transaction retry:

- `Snapshot`  
    Because the transaction keeps the same transaction-start snapshot, so you normally need a **new transaction** to retry meaningfully. ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql?view=sql-server-ver17&utm_source=chatgpt.com "SET TRANSACTION ISOLATION LEVEL (Transact-SQL)"))
    

## One very practical mental model

Ask this after a failure:

**If I stay in the same transaction and query again, can I see a newer committed version that might let the retry succeed?**

- Under `ReadCommitted` / RCSI: often **yes**. Same-transaction retry can make sense. ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql?view=sql-server-ver17&utm_source=chatgpt.com "SET TRANSACTION ISOLATION LEVEL (Transact-SQL)"))
    
- Under `Snapshot`: usually **no**, because the snapshot is fixed at transaction start. Start a new transaction. ([Microsoft Learn](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-transaction-isolation-level-transact-sql?view=sql-server-ver17&utm_source=chatgpt.com "SET TRANSACTION ISOLATION LEVEL (Transact-SQL)"))
    
- Under `RepeatableRead` / `Serializable`: usually **not helpfully**, because you are preserving the same lock-based transaction context. Start over if retry is needed, and keep such transactions short.
