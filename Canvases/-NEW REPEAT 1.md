1 Single-responsibility principle
Одна функция или метод имплементирует одну единицу поведения 
- Один повод для изменения (одна ось изменеия) - представить что 
- В одной функции то, что должно меняться вместе
- Функционал одной оси изменения также не может быть разбросан по всему коду, а должен быть в одном месте чтобы не приходилось его выискивать

Для чего:
1 Для декаплинга, чтобы не было сильной зависимости и при изменинии одной части кода не приходилось менять другую + чтобы люди работающие над другим поведением не лезли в функцию
2 чтобы было удобнее тестировать
3 чтобы было понятно какая функция что делает и была удобная навигация(не приходилось выискивать функционал нужный в несвязанных классах)

2 Open-closed principle
Нужно писать код так чтобы новый функционал можно было добавлять не изменяя текущий код

Как?
1 Используя интерфейсы в функциях/конструкторах чтобы можно было подставить другую реализацию 
2 создавая generic функции, поведение которых можно изменить передав в них другой параметр, ну и так же с конструкторами 

Для чего: 
1 чтобы не переписывать код и тесты
2 чтобы не сталкиваться с новыми ошибками 

3 Liskov substitution principle 
Дочерние классы должны иметь весь функционал базового 

- Если функция принимает базовый класс то туда можно подставить любой из дочерних и все должно работать 
- Не нужно внутри такой функции проверять какого типа этот класс и использовать функции принадлежащие конкретному дочернему классу, в такой ситуации нужно создать отдельную функцию принимающую дочерний класс
4 Interface segregation principle 
Интерфес должен предоставлять только те методы которые характеризуют его поведение
- Лучше сделать несколько интерфейсов предоставляющих разное поведение чем один большой 
- Интерфейс принадлежит не серверу а клиенту и предоставляет то что клиенту нужно 
- Представить ситуацию где нужно изменить имплементацию какого то определенного поведения и придется ещё возиться с тем что с этим не связано
5 Dependency inversion principle
Зависимость на интерфейсах а не на реализации 
- Использовать везде интерфейсы вместо реализаций(реальных классов)
1 чтобы можно было изменить реализацию
2 чтобы при изменении реализации не приходилось переписывать места где присутствует зависимость на этой реализации а не на интерфейсе 
3 чтобы можно было протестировать
